## §4. Amendment Types

### 4.1 Refinement
A minor wording modification designed to clear semantic ambiguity or update a technical tool name without altering underlying security boundaries or tier constraints.

### 4.2 Addition
The injection of an entirely new operational section, metric circuit, or defense sub-clause into an un-allocated slot or within an existing open section.

### 4.3 Extension
The formal population of a reserved placeholder (Sections 13, 14, or 15) to transition a dormant ecosystem layer into active, running code.

### 4.4 Removal
The permanent deletion of an operational sub-clause. Removals carry the highest legislative bar and cannot be executed if the deletion implicitly weakens an adjacent defense perimeter. Any proposal seeking to lower a compliance threshold or remove a safety check is classified as a relaxation and is strictly prohibited by Locked Constant #8.

## §5. Proposal Process

### 5.1 Drafting Rules
Every proposed amendment must be submitted as a structured, self-contained proposal payload. The draft must explicitly state:
- The target section and exact line numbers slated for modification.
- The precise text to be injected or deleted.
- A comprehensive technical justification mapping the change against active cluster threat models.

### 5.2 Consent Citation Alignment
All amendment proposals are designated as Tier 3 actions. They must be explicitly formatted to include a blank signature token line adhering to the mandatory **Reading II Protocol Syntax**: `<consent_word> msg:<id> @<HH:MM>`.

## §6. Pre-Flight Checklist (The Cross-Document Sync Rule)
To prevent runtime errors, peer attestation faults, and automatic cluster deadlocks, every proposed amendment must pass a mandatory, programmatically enforced pre-flight checklist prior to human submission.

### 6.1 The Dual-Document Propagation Mandate
An amendment can never exist as a single-document text change. The proposal must generate paired, synchronized diffs for two separate target destinations within a single batch:
1. **The Full Master Diff:** The comprehensive, long-form Markdown expansion for insertion into `ARMY_MISSION.md`.
2. **The Compressed Runtime Diff:** The highly dense, token-optimized summary rule for insertion into the `CLAUDE.md` context block.

### 6.2 Pre-Flight Verification Ledger
The staging script must physically verify that the changes across both documents match line-for-line in semantic intent. The proposed new file hashes for both target destinations must be pre-calculated and recorded together inside the proposal payload body. If the compilation script detects a mismatch or an un-propagated rule between the master file and the agent context block, the proposal is structurally invalid and is blocked from submission.

### 6.6 Bootstrap Pattern
Carried forward from v1.5 conventions, the system preserves the bootstrap modification pattern. When an amendment alters a script baseline or hook configuration, the rule change must be written to disk in a deactivated state, cryptographically verified by neighboring nodes via peer attestation, and then activated simultaneously cluster-wide via a signed systemd daemon reload token.

## §8. Implementation Steps
Once a Reading II token and a verbal phrase signature are verified by the cluster, the installation sequence executes via a strict **Rebaseline-First** pipeline:

1. **Staging Commit:** The synchronized diffs are simultaneously written to the `/proposed/` directory.
2. **Access Control Audit:** The configuration script performs an immediate audit against `basement.delegations` to verify that no unauthorized user processes are active in the workspace during the write operation.
3. **Signature Rebaseline:** The script rewrites the target system files, recalculates the new SHA-256 hashes for both `ARMY_MISSION.md` and `CLAUDE.md`, and overwrites `basement.hashes`.
4. **OS-Layer Immutability Binding:** The system re-applies file system immutability flags (`chattr +i`) across all updated sacred paths.
5. **Cluster Restart:** The systemd service layers execute a coordinated agent cluster restart, forcing all running nodes to boot fresh, verify their startup hashes against the newly updated ledger, and pull the synchronized context directly into short-term memory.

### 8.9 Hash Rebaseline Cadence
Preserved from v1.7, the system maintains a silent background cron job that continuously hashes all doctrine files every 300 seconds, matching local states against `basement.hashes` to detect and instantly isolate any silent disk corruption or unauthorized host-level modifications.
